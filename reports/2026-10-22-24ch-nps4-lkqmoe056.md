# 2026-10-22：lkqmoe 0.5.6 + 24 通道内存、NPS4（GLM-5.3）

## 变化

- 内存补满到 24 × 16 GiB DDR5-4800（384 GiB），BIOS 改 NPS4（8 个 NUMA 节点）。
- `lkqmoe/` 换成 0.5.6 编译版，与 lsglang_ds4.1 是同一份（AVX512 库 `-DLKQMOE_DOWN_R4=1`）；`python/sitecustomize.py` 支持 `LKQMOE_MAIN_CPUS=auto`。
- 新增 `launch/run-glm53-nvfp4-24ch-nps4.sh`：主线程用 `LKQMOE_MAIN_CPUS=auto`（允许的 CPU − 专家线程 − 信箱调度线程，NPS4 下 15 个逻辑 CPU，与专家线程零重叠）。
  原脚本里按 NPS2 写的列表在 NPS4 下会与 lkqmoe ≥ 0.5.2 的专家线程重叠，所以保留给 20 通道 / NPS2 用。

- 0.5.0 只认 4 个 NUMA 节点，在 NPS4 下把权重都放在一颗 CPU 上，另一颗 CPU 的线程跨插槽读，CPU 专家慢 2–3 倍；0.5.6 按 8 个节点放。
- 两种 Down 构建（一次读 4 行 / 1 行）输出逐位相同；本仓库用一行版，三个模型共用一份二进制。

- 并发：1 个请求 78.1 → 82.5 tok/s；2 个请求合计 101.6 → 112.4 tok/s（每个 58.0）。
- 温度 1.0（`bench/spec_t1_bench.py`）：83.3 → **84.8 tok/s**。
- 困惑度 4.0580 → 4.0598，各长度都找回埋藏事实；显存峰值与之前相同。
- GLM 开着自适应草稿步数（1–5 步，按实测代价选），CPU 变快后它会选更多步：接受长度约 3.3 → 4.1，每步更贵但每步产出更多，所以看 decode tok/s。
- 首 token 各长度与之前一致：长预填充受 GPU 计算和 PCIe 上传限制，不受内存通道影响。

## GPU 与 CPU 谁在等谁（WebUI 正式启动后，只开 GPU 的 40 步剖析）

- 42 个 MoE 层每步各一次 CPU 专家调用；GPU 热池内核每次平均 145 µs，GPU 等 CPU 平均 206 µs（中位 180 µs）。
- 99.9% 的调用里 GPU 都在等 CPU；每步热池 6.1 ms、等 CPU 8.7 ms。GLM 的 decode 受 CPU 专家（内存带宽）限制，
  所以 24 通道和 0.5.6 的 NUMA 放置对它有效，后续提速也主要在 CPU 侧。
